# Audit di riproducibilità Allen–Cahn OOFEM

## Perimetro

Valutazione statica di [`validation_inventory.md`](validation_inventory.md) e [`validation_metrics_audit.md`](validation_metrics_audit.md), dei runner e delle istruzioni collegate. Non sono state eseguite simulazioni e non sono stati modificati input, codice, CSV o output originali. Gli artefatti MMS e WED non sono considerati test riproducibili in questo audit.

Gli stati descrivono la possibilità di ripetere il test e rigenerare le sue metriche principali dai file/istruzioni disponibili; non sono giudizi sulla correttezza scientifica:

- **REPRODUCIBLE**: tutti gli input, riferimenti, analisi, dipendenze e istruzioni essenziali sono disponibili e la versione è identificabile senza ambiguità.
- **REPRODUCIBLE WITH MINOR FIXES**: la procedura è ricostruibile, ma servono accorgimenti documentali o di configurazione (per esempio build/path espliciti o directory output nuove).
- **INCOMPLETE**: manca un raw output/riferimento necessario, il runner non è isolabile, oppure passaggi manuali non sono specificati.
- **NOT ASSESSABLE**: gli artefatti non descrivono un test quantitativo riproducibile o non consentono di determinarne l'esecuzione.

## Controlli trasversali

### Percorsi assoluti e dati temporanei

- Percorsi `/tmp` rendono gli script legati a una convenzione POSIX e possono puntare a cartelle vuote su un altro account/macchina: `run_energy_balance.py` e `update_report_assets.py` usano `/tmp/stvowu_energy_balance`; `analyze_energy.py` punta a `/tmp/stvowu_validation`; i runner/analizzatori Okumura e Xiao usano directory `/tmp` fisse; `compare_paper_figures.py` assume `/tmp/ac_paperplots` se non si passa `--data-root`.
- [`digitize_okumura_fig44.py`](literature_comparison/digitize_okumura_fig44.py) ha come default un PDF in `/home/marco/.../refs/`; benché esista `--pdf`, il README non dà istruzioni per procurarsi il PDF e passare il percorso.
- I runner interni al repository risolvono di norma il repo rispetto a `__file__`, ma fissano il binario a `build/debug_magneto/oofem`; Lee usa `build/opt_magneto/oofem`. Manca una selezione comune di `OOFEM_BIN` e una procedura di build ripetibile per questi target.

### Output, sovrascritture e nomi

- Molti runner usano `mkdir(exist_ok=True)` e poi riscrivono `case.in`, log, CSV e figure. Rientrano qui `run_case.py`/`run_suite.py` parabolici, `run_energy_validation.py`, runner hyperbolic bulk/kink/Nizovtseva/coupled, script letterari e Lee. La riproduzione va indirizzata a una cartella nuova; il repository non applica un manifest che impedisca di mescolare parametri e raw di run precedenti.
- `run_suite.py` riscrive `case.in` prima di controllare se output/log precedenti sono completi, poi può saltare il run guardando solo file finale e testo `ANALYSIS FINISHED`. Non confronta il contenuto dell'input scritto con quello che ha prodotto il VTU: può associare un nuovo input a vecchi risultati.
- `run_energy_validation.py` può isolare i raw con `OOFEM_ENERGY_OUT` e rinominare i CSV con `OOFEM_ENERGY_PREFIX`, ma tali opzioni non sono spiegate nei report; i CSV sono scritti con modalità `w` e sovrascritti.
- `run_coupled_independent.py`, `run_coupled_refinement.py`, `run_bulk_references.py`, `run_stationary_kink.py`, `validate_nizovtseva_bulk.py` sovrascrivono folder/output esistenti senza errore. Lo script `postprocess_energy.py` è un'eccezione positiva: apre il CSV con modalità esclusiva e rifiuta overwrite.
- Il prefisso dichiarato nell'input è generalmente coerente col pattern `.out.m0.*.vtu`; tuttavia `analyze_xiao_chen_case4.py` cerca output in path `/tmp` convenzionali e ha un fallback solo per un singolo file N20/dt=0.0001. `analyze_energy.py` legge un'altra cartella `/tmp` non generata dal suo input associato. Il report parabolico 2D ha un link errato al CSV energia nella cartella padre.

### Versioni e dipendenze

- Gli header `.out` identificano OOFEM, ma la build documentata è `rel-2.1-5430-g2cc1a7706-dirty`; l'audit cita il base hash `0680f2da49050e2ef72407897d7b292ce66cd054`. Non è un checkout pulito né una ricetta che ricostruisca la stessa build: un altro ricercatore può ripetere il flusso, ma non garantire bitwise la stessa revisione.
- Dipendenze riportate: Python 3.12.3, NumPy 1.26.4, SciPy 1.11.4, Matplotlib 3.6.3; DOP853 usa SciPy. La digitalizzazione Okumura richiede Pillow e `pdftoppm`; alcuni PDF/riferimenti sono esterni. I README non offrono un `requirements.txt`, lockfile o container per la parte Allen–Cahn OOFEM.
- Le istruzioni sono distribuite tra [`README.md`](README.md), README hyperbolic, README letteratura, report e commenti nei runner. Il README generale è centrato su WED/MMS e non costituisce una guida OOFEM no-MMS autonoma. Per diversi script i comandi sono inferibili dal nome del runner, ma non elencati esplicitamente.

## Correzioni documentali minime

1. Aggiungere una guida OOFEM Allen–Cahn che elenchi per ogni test comando di esecuzione, comando di analisi, dipendenze, riferimento, input/IC/BC e file/figura prodotti; tenere fuori WED e MMS.
2. Documentare build/commit pulito e usare `OOFEM_BIN` o un target unico verificato; aggiungere versioni Python dipendenti.
3. Per ogni runner indicare chiaramente che sovrascrive dati o richiede directory vuota, e fornire un output root esplicito; non modificare i risultati storici.
4. Spiegare l'ordine dei passaggi `run -> postprocess -> figures`, specialmente per bilancio 20×20, Okumura, Xiao e paper comparison. Rendere il PDF Okumura un argomento/risorsa esplicita e sostituire le istruzioni `/tmp` con percorsi scelti dall'utente.
5. Non chiamare i test energetici iperbolici “riproducibili per energia totale” finché non è disponibile la velocità richiesta; documentare l'esempio attuale come soli contributi potenziali.
